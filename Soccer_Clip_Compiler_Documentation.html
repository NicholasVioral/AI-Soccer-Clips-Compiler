Soccer Clip Compiler — Complete Project Documentation

A full-stack web application that automatically generates soccer highlight reels from broadcast match footage.

Repository: NicholasVioral/AI-Soccer-Clips-Compiler  •  Author: Nicholas Vioral  •  Document generated: 2026-06-24

1. One-Paragraph Summary

Soccer Clip Compiler lets you upload a recording of a soccer match, automatically match it against StatsBomb's professional event dataset, sync the video's clock to real match time, browse every on-ball moment in the game, and export a single compiled MP4 of exactly the plays you care about — in seconds. It bridges a gap between two worlds: StatsBomb publishes detailed, free, frame-by-frame event data for real matches (every pass, shot, dribble, carry), and broadcast video has all the footage — but the two don't share a clock. This app's core engineering job is to align them, then use the event data as a "table of contents" for the video.

2. What It Does — End-to-End Workflow

  1. Upload a match video — drag-and-drop, or select a file already sitting on the server (this bypasses browser/proxy upload limits for very large 1080p files that can be tens of GB).
  2. Auto-identify the match — OCR reads the scoreboard from sampled video frames to detect the team names, and/or the filename is parsed; the detected teams are fuzzy-matched against the StatsBomb open dataset.
  3. Sync events to the video — the user marks the kickoff moment for each half independently, giving the app a precise video-to-match-time offset per half that correctly handles the halftime break. (An automatic OCR clock-scan path also exists.)
  4. Browse every event — the full StatsBomb event stream (roughly 3,500+ events per match) loads into a filterable, searchable list and a seekable dot timeline. Click any event to jump the video to that exact moment.
  5. Select and generate clips — pick a player and the event types you want (shots, passes, dribbles, etc.), set padding, and hit Generate.
  6. Download — a single compiled highlight MP4 arrives in seconds.

Smart Clip Boundaries

Clips are not a fixed time window around an event. The app analyzes the full event stream to find natural possession boundaries:

  • Clip start — scans backward to find the Ball Receipt* event that began the player's current possession, so the clip opens when the ball arrives at their feet, not seconds into their run.
  • Clip end, which varies by event type:
    • Pass → ends when the next player receives the ball + 2 s (you see the full pass and where it lands).
    • Shot → keeps a 10 s minimum so the outcome (goal/save/miss) is always visible.
    • Other events → end at the first possession event by a different player + 1 s.

    ├── ocr_engine.py       # Frame extraction + Tesseract OCR preprocessing
    ├── statsbomb_client.py # statsbombpy wrapper + caching + fuzzy search

app.py — Creates the Flask app, registers four blueprints all under the /api prefix, sets a 2 GB max upload size, and creates the uploads/ and clips/ folders on startup. CORS is locked to a single origin read from the FRONTEND_URL environment variable (falls back to http://localhost:3000 for local dev) so the production domain is never hardcoded. The dev server runs with use_reloader=False to stop Werkzeug's file watcher from constantly restarting when it sees changes in large site-packages installs.

Clip generation pipeline (clip_extractor.py):

  1. For each selected event, _to_video_time() converts match seconds → video seconds using either the OCR clock map (linear interpolation, with up-to-10-minute extrapolation past the last reading) or the per-half manual offset keyed by event.period.
  2. Scan backward through all events to find the Ball Receipt* that opened this possession (clip start), skipping non-possession events (Pressure, Foul) by other players and stopping at another player's possession event. Never looks back more than 60 s.
  3. Scan forward to find the natural clip end based on event type (Pass vs Shot vs other), with a minimum-duration floor.
  4. FFmpeg cuts each segment. Each clip is cut with output-side -ss after -i for frame accuracy plus -c copy for no re-encoding, and -movflags +faststart.
  5. FFmpeg concatenates all segments into one MP4 via the concat demuxer. Overlapping/adjacent segments are merged first so the reel has no duplicate footage.

A POSSESSION_EVENTS frozenset (Ball Receipt*, Carry, Dribble, Shot, Pass, Goal Keeper, Dribbled Past, Miscontrol) distinguishes possession from non-possession events during the backward/forward scans.

Broadcast clock scanner (clock_scanner.py + ocr_engine.py):

  1. Samples ~8 probe frames and tries three horizontal crop regions (top-left, top-center, top-right) to auto-detect where the broadcast clock lives — broadcasters place it differently.
  2. Samples the detected region roughly every 15 s across the full video.
  3. Runs Tesseract OCR with multiple preprocessing variants (grayscale, inverted, contrast-boosted) on each frame.
  4. Parses an MM:SS regex — handles added time (e.g. 90+3) and the "frozen 90:00" some broadcasts show after full time.
  5. Outputs a clock_map: a list of {match_seconds, video_seconds} pairs used for linear interpolation everywhere downstream.

The toVideoTime(matchSeconds, period) function in App.jsx is the single source of truth for converting match time to video time. Every component — timeline, event list, clip generator — calls it. When the clock map is available it interpolates; otherwise it falls back to the per-half manual offset. Centralizing this (along with the isSynced flag) eliminated an entire class of "why does the timeline show different times than the event list?" bugs.

6. The Core Engineering Challenges

6.1 The Sync Problem (the heart of the project)

StatsBomb gives match timestamps (minutes/seconds into the game). A broadcast video has its own clock — it starts at 00:00 when you press record, not when the referee blows the whistle. Aligning the two was the central problem.

  • First approach — single kickoff offset: measure how many seconds into the video the match starts, add that to every event. Worked for the first half, broke completely for the second, because broadcasts include a variable-length halftime break that one offset can't model.
  • Solution — per-half calibration: the user marks the kickoff moment for each half independently, giving two offsets. event.period selects which one to apply.
  • More ambitious — OCR automatic sync: sample frames every 15 s, read the on-screen clock with Tesseract, build a full match_time → video_time lookup table that even survives replays and broadcast cuts. Production-readiness required auto-detecting the scoreboard region, multiple OCR preprocessing variants, added-time/frozen-clock handling, and extrapolation into stoppage time. In practice the manual per-half sync remains the more reliable default; auto-OCR scan was made opt-in.

6.2 Large File Handling

A full-match 1080p recording can be tens of GB, exceeding browser and proxy upload limits. The solution: a server-side file registration endpoint (POST /api/upload/register) — drop the file directly into the uploads folder, tell the app the filename, and it registers it with zero data transfer, plus a file-picker UI listing what's already on the server.

6.3 Clip Quality

The original fixed padding_before/padding_after approach produced clips that were technically correct but hollow — too much build-up and post-event dead air. The possession-boundary algorithm (scan back for Ball Receipt*, scan forward for the next possession event) gives clips a clear narrative shape: the ball arrives, the action happens, the ball leaves.

6.4 FFmpeg Performance

Switching from re-encoding (libx264 ultrafast) to stream copy (-c copy) cut clip generation from several minutes to under ~5 s for 1080p footage. The trade-off is that input-side seeks land on keyframe boundaries; the possession-start padding hides any early-cut artifacts, while output-side -ss is used where frame accuracy matters.

9. What I Learned

  • FFmpeg stream copy is massively underrated — -c copy took clip generation from minutes to seconds; keyframe-boundary cuts are hidden by possession-start padding.
  • OCR on broadcast video is harder than it looks — fonts vary by broadcaster, scoreboards animate, overlays corrupt pixels, and the clock can sit in three different positions. Robustness needed multiple crop regions, preprocessing variants, and regex patterns — and even then, manual sync is the more reliable production path.
  • Event-driven sports data has real semantic structure — StatsBomb events form a possession graph (Ball Receipt* → Carry → Pass → Ball Receipt*). Treating it as a graph and scanning along it makes natural clip boundaries emerge from the data instead of arbitrary padding.
  • React state architecture matters early — centralizing toVideoTime() and isSynced in App.jsx killed a whole class of time-mismatch bugs.
  • Scope creep is real — the project grew from "cut a clip at a timestamp" to OCR clock scanning, per-half sync, server file registration, smart possession boundaries, and a full event timeline; each feature had to integrate carefully with the sync pipeline.

10. How It Could Be Improved (Roadmap)

Accuracy: train a small object-detection model to locate the scoreboard reliably (kill the multi-region probing); use optical flow on the video itself as a second signal for possession boundaries; auto-detect kickoff via the center-circle ball-placement frame.

Features: support multiple video files per match (route clips by event.period); clip preview/thumbnails before export; custom clip ordering; team color-coding + filter on the timeline; one-click export presets ("Shot compilation", "Key passes", "Full press sequence").

Scale: move generation to a Celery/Redis background queue with WebSocket progress; database-backed sessions (SQLite/Postgres) so users can save and return; cloud storage (S3) for uploads and clips.

Data: integrate Wyscout or Opta to go beyond StatsBomb's curated competitions; let users tag custom moments ("tactical foul", "press trigger") as first-class events.

12. Data & Licensing

Uses StatsBomb open data, freely available under the StatsBomb Open Data Licence. No API key is required. The statsbombpy client wraps it; results are cached (~30-min TTL) and DataFrame output is cleaned into JSON-friendly event objects.
